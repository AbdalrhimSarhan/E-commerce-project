# منهجيتي الهندسية في هذا المشروع

> هذه نسخة عربية تشرح طريقتي في العمل على المشروع. التقرير الرسمي هو
> [docs/ai-development-report.md](ai-development-report.md) (بالإنجليزية).
> كل ما هنا قابل للتحقق من المستودع: [docs/prompt-1.md](prompt-1.md)،
> وتقارير المراحل في [docs/reports/](reports/)، والكود، وسجل Git.

## 1. طريقة العمل

- خططت للـ architecture وللـ data model في جلسة تخطيط منفصلة **قبل كتابة أي كود**.
- بعدها أعطيت الـ coding agent تعليمات مكتوبة مقسمة إلى مراحل، أولها موجود في
  [docs/prompt-1.md](prompt-1.md). حددت فيها الـ stack، وقواعد قاعدة البيانات،
  وشكل الـ response الموحد، والـ error codes، وقواعد عمل صارمة: مرحلة واحدة في
  كل مرة، ولا يشغّل الـ agent أي أمر Git، ويسأل بدل أن يفترض.
- في المرحلتين 0 و1 كان التوقف إلزاميًا: لا ينتقل الـ agent للمرحلة التالية حتى
  أتحقق من السابقة وأرد بكلمة "APPROVED". بعد اعتماد المرحلة 1، وبسبب ضيق الوقت،
  قررت أن تُبنى بقية مراحل الـ API دفعة واحدة، ثم راجعتها واختبرتها. وكان الـ MCP
  server مرحلة واحدة بتعليمات مستقلة وتقرير نهائي.
- بعد كل مرحلة كتب الـ agent تقريرًا في [docs/reports/](reports/): ملخص،
  والملفات، والقرارات التي لم تحددها التعليمات، وأوامر التحقق، وقسم فارغ لمراجعتي.
  واختبرت كل مرحلة بنفسي.

## 2. قاعدة البيانات

الـ coding agent لم يصمم الـ schema. صممت كل جدول وحقل وعلاقة في جلسة التخطيط،
وسألت عن حالات محددة وناقشت المقترحات حتى اتخذت كل قرار:

- **TypeORM بدل Prisma**، وكل تغيير في الـ schema يمر عبر migrations فقط، و
  `synchronize` دائمًا `false`.
- **حذفت `slug` من الـ categories** لأنه غير ضروري لـ API، و**أبقيت `sku`** كمعرّف
  تجاري فريد للمنتج.
- **علاقة many-to-many بين المنتجات والفئات**، بعد مقارنتها بـ one-to-many. السبب:
  الـ agent يستطيع إدارة الروابط دون أن يلمس جدول المنتجات إطلاقًا (حد صلاحيات
  واضح)، وحذف فئة يحذف روابطها فقط ولا يحذف أي منتج.
- **جدول الربط** بـ composite primary key هو `(product_id, category_id)`، مع index على
  `category_id`. وحذفت منه `created_by`، لأن الـ audit log هو المصدر الوحيد لمعرفة
  من فعل ماذا.
- **في `audit_logs` حذفت عمود "source"**، لأن طريقة المصادقة تثبت أصلًا من أين جاء
  الطلب، أما header يرسله العميل فيمكن تزويره.
- **لاحظت تناقضًا في التصميم الأول:** للمستخدمين `is_active`، لكن `audit_logs` كان
  بلا foreign key "تحسبًا لحذف مستخدم". حسمت الأمر: المستخدمون لا يُحذفون نهائيًا
  أبدًا، بل يُعطّلون فقط. لذلك صار لـ `audit_logs.actor_id` قيد foreign key مع
  `ON DELETE RESTRICT`، فتضمن قاعدة البيانات نفسها أن سجل التدقيق لا يفقد صاحبه أبدًا.
- **قررت تسجيل محاولات الرفض (403) أيضًا**، لتتبّع agent يحاول تنفيذ ما لا يُسمح له به.
- **المعرّفات (ids):** فكرت في التحول إلى أرقام متسلسلة لتسهيل العرض، ثم رفضت ذلك.
  تبقى الـ UUIDs، وتستخدم بيانات العرض (demo data) UUIDs ثابتة سهلة القراءة بدلًا منها.

## 3. المصادقة والصلاحيات

- **عمود role بسيط بدل جداول RBAC.**
- **أضفت دور `super_admin`** ليتمكن دور أعلى من تعطيل الـ admins والـ agents. ولا
  يمكن تعطيل `super_admin` عبر الـ API، فلا يوجد خطر أن يُغلق النظام على نفسه.
- **JWT مع جدول sessions على السيرفر**، فيسري الـ logout والتعطيل فورًا.
- **المصادقة في middleware والصلاحيات في guards** بمبدأ fail-closed: أي route محمي
  بلا `@Roles` يُرفض.
- **الـ AI agents هوية مستقلة** بـ API keys مخزنة كـ hash، وبأقل صلاحيات يحتاجونها،
  وليسوا حساب admin.
- **قصرت قراءة الـ audit log على `super_admin` وحده (separation of duties):** الـ admin
  هو من ينفّذ التعديلات على المنتجات والفئات، فلا يصح أن يكون هو نفسه من يراجع سجل
  تلك التعديلات. لذلك يحصل الـ admin والـ user والـ agent على 403 عند محاولة قراءته.

## 4. الـ MCP server

- الـ MCP server **عميل خالص للـ REST API**، لذلك لا يستطيع تجاوز الـ validation أو
  الصلاحيات أو الـ audit.
- **Streamable HTTP مع key passthrough:** الـ MCP server لا يخزن أي سر.
- **لا توجد tools لكتابة المنتجات**، لأن الـ agent لا يملك هذه الصلاحية.
- **SDK v2**، وهو الإصدار الحالي للبروتوكول.

## 5. كيف راجعت عمل الـ agent (وقائع حقيقية)

- **رفضت خطة من 9 commits صغيرة**، ثم لاحقًا تقسيمًا كان فيه commit لا يعمل
  build. قاعدتي: كل commit وحدة تعمل ويمكن التحقق منها.
- **راجعت الـ migration الناتجة والـ constraints في psql** قبل قبولها، وقبلت
  constraints الـ CHECK الأشد التي اقترحها الـ agent بعد مراجعتها.
- **درس تعلمته:** أثناء اختبار الـ agent للـ seed كنت أشغّل builds وأعدّل `.env` في
  نفس الوقت، فلم تعد كلمة مرور قاعدة البيانات مطابقة، وظل `dist` يُعاد بناؤه.
  منذ ذلك الحين لا أشغّل أي أمر بينما يتحقق الـ agent.
- **اختبرت الـ MCP server بنفسي** بـ MCP Inspector (الأدوات العشر كلها، والأخطاء،
  ومفتاح خاطئ)، وبـ AI client حقيقي داخل VS Code، وتحققت من سجلات الـ audit الناتجة.
